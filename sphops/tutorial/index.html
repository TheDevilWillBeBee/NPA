How NPA's SPH perception became fast

This guide explains the CUDA code that computes perception in Neural Particle Automata (NPA). First it explains the original hash-grid kernels. Then it shows the first fused version. Then it goes through six changes. Together, they made fused perception 4 to 6 times faster on the GPU and training about 1.7 times faster.

Setup for all numbers, unless a section says otherwise: RTX 4090, 2D, a batch of 8 × 4,096 particles, 16 state channels, at most 32 particles per grid block. "Before" means the first fused version. "Original" means the original unfused code.

4.4× / 6.1×
faster GPU time for fused perception (forward / backward), average of four kinds of workloads
1.68×

2.3–2.4×
faster training than the original, unfused SPH operators

Before we startWords used here

Kernel
A function that runs on the GPU. In SPH, "kernel" also means the weight function W. This guide says "SPH kernel" for that.
Warp, lane
A warp is a group of 32 GPU threads that run the same instruction together. A lane is one thread of a warp.
Block, SM
A CUDA block is a group of warps that runs on one SM (one of the GPU's processors). The RTX 4090 has 128 SMs.
Shared memory
Small, fast memory that all threads of one CUDA block can use.
Register, spill
Registers are the fastest memory. Each thread has its own. If a thread needs too many, extra values go to slow memory. This is called a spill.
Occupancy
How many warps are active on an SM, compared with the maximum. While one warp waits for memory, the SM runs another one. So more warps can hide waiting time.
Host, sync
The host is the CPU side (Python and C++). A host sync means the CPU stops and waits until the GPU finishes its work.

BackgroundWhat perception computes

Each particle i has a position xi, a mass mi (fixed during training), and a state si with C channels. Perception looks at all neighbors closer than the radius ε. It uses two SPH kernels: the smooth poly6 kernel W and the gradient of the spiky kernel, ∇W.

  • Density: ρi = Σj mj W(rij). Each particle then has a volume Vj = mj / ρj.
  • Blur: s̄i = Σj Vj sj W(rij).
  • State gradient: ∇si = Σj Vj (sj − si) ∇W(rij). It is corrected with the inverse of the moment matrix Mi = Σj Vj ∇W(rij) ⊗ rij. The correction only changes the forward value. The backward pass ignores it (a straight-through estimator).
  • Density gradient: ∇ρi = Σj mj ∇W(rij).
  • Scaling: the state gradient is multiplied by ε/ε0. The density gradient is multiplied by (ε/ε0)D+1 and divided by the total mass of the sample, Σj mj. With unit masses, the total mass is N. This way the density gradient does not depend on the number of particles. Then both gradients get a log normalization: log(1 + |g|) · g / |g|.

The output for each particle is [s, s̄, ∇s, ∇ρ]. It has C(2 + D) + D numbers (66 for C = 16 in 2D), and the NPA's MLP reads it. One training epoch runs 16 to 95 steps, and the backward pass goes through all of them.

All of these are sums over neighbors. So the cost depends on how many neighbors each particle has. The benchmark uses the cases that training really sees:

CaseBoundary and radiusNeighbors per particle
Disk seed for growing (radius 0.2)clamped, ε = 0.1823
Growing disks (radius 0.4 and 0.6)clamped, ε = 0.1107–227

The disk seed is the hardest case. In one call there are about 62 million candidate pairs to check, and about 26 million of them are inside the radius.

The starting pointThe original grid kernels

The original sph_cuda.cu has two modes. The "particle" mode sorts particles in Morton order. The "grid" mode is used by NPA's 2D configs. This section explains the grid mode. All later versions still use its main ideas.

Sorting particles into cells

The cell size of the grid is equal to the radius ε. So all neighbors of a particle are in its own cell or in one of the 8 cells around it (26 in 3D). The code reorders the particles, so that particles of the same cell are next to each other in memory. This is a counting sort with three passes:

The count pass uses one thread per particle. Each thread does an atomicAdd on the counter of its cell. Then the original code ran a second pass with a second atomicAdd, to find the place of each particle inside its cell. Step 4 removes this second atomic.

Original count pass (grid mode)
uint32_t prev_count = atomicAdd(&cell_counts[cell_idx], 1U);
if (prev_count % config.MAX_PARTICLES_PER_BLOCK == 0)
    atomicAdd(&blocks_per_cell[cell_idx], 1U);   // one more grid block for this cell

Neighbors are three ranges in memory

Cells are numbered so that x changes fastest. So the three cells in one row of the 3×3 neighborhood are next to each other in memory. The kernel does not need nine lookups. It reads three ranges of particles, one per row, from bin_offsets[first] to bin_offsets[last + 1]. With periodic boundaries, a row can cross the edge of the domain. Then the code reads a second range for the part that wraps around.

Grid blocks

A dense cell can have hundreds of particles. So each cell is split into grid blocks, with at most max_particles_per_block particles each (32 in the training configs). A small BlockInfo record describes each grid block: the cell, the offset inside the cell, the number of particles, and the batch index. One CUDA block processes one grid block.

Only the GPU knows how many grid blocks there are, because it counts the particles. So the code launches enough CUDA blocks for the worst case. Unused blocks have zero particles and stop at once.

One kernel for each operator

Each SPH operator (count, density, blur, gradient, density gradient, moment matrix) is a version of one template kernel. Each one also has a backward kernel. A CUDA block first copies its own particles into shared memory. Then it goes through the three neighbor ranges in tiles of 128 particles, which it also copies to shared memory. Each thread computes one output value, for one (particle, feature) pair:

Original grid forward, blur part (one thread per particle and feature)
for (uint32_t i = threadIdx.x; i < local_chunk * feature_dim; i += blockDim.x) {
    uint32_t particle_idx = i / feature_dim, feature_idx = i % feature_dim;
    ParticlePosition<DIM> p_i = local_pos[particle_idx];
    float output = 0.0f;
    for (uint32_t j = 0; j < remote_chunk; ++j) {
        ParticlePosition<DIM> p_j = neighbor_pos[j];
        if (config.l2_distance(p_i, p_j) < eps2) {       // every thread tests the distance
            float v_j = neighbor_density_rcp[j];
            float s_j = neighbor_state[j * feature_dim + feature_idx];
            ParticlePosition<DIM> r_ij = config.displacement(p_i, p_j);
            float w_ij = smoothing_kernel(r_ij, config.eps);
            output += s_j * w_ij * v_j;
        }
    }
    local_buffer[i] += output * config.smoothing_coef;
}

In the original code, models/npa.py builds perception from these operators in PyTorch: density, blur, the moment matrix and its inverse, the gradient with the straight-through correction, the density gradient, scaling, log normalization, and concatenation. So the forward pass goes over all neighbors five times, and the backward pass five more times.

The backward kernels also gather: each particle collects its own gradient from its neighbors, because the pair terms are symmetric. Several feature threads add to the gradient of the same particle (for position and density). They use atomicAdd into a shared-memory buffer, and then write the result to global memory once. This design is general. It gives gradients for everything, also for positions and densities.

Step 0The first fused version

The first optimization was written with ChatGPT, in perception.cuh. It fuses perception for the setting that NPA trains with: fixed masses, positions without gradients (detached), and gradients only for the states. It uses four kernels instead of five passes over the neighbors:

KernelWhat it computesThreads per particle
density_forwarddensity, density gradient, volumesone warp (32 lanes)
forwardblur, gradient, moments, correction, normalization, output16 lanes, one per channel (C = 16)
backward_preparebackward of the normalization, self termsone thread per channel
backwardbackward of blur and gradient16 lanes, one per channel

Positions have no gradient, so the backward only needs the gradient for the states. It gets the blur part and the gradient part in one pass over the neighbors. This version also pads other channel counts to 4, 8, 16, or 32, and it saves the values that the normalization backward needs. With it, training became 1.3 to 1.5 times faster.

In the forward kernel, each channel has its own lane. For each pair, lane 0 computes the distance and the weights W and ∇W. Then warp shuffles send these values to the other 15 lanes:

First fused forward, inner loop (one lane per channel)
for (unsigned int j = 0; j < count; ++j) {
    float weight = 0.0f, grad_weight[DIM] = {0.0f};
    if (valid && channel == 0) {                       // only lane 0 of 16 does this
        pair_weights(config, position, neighbor_pos[j], weight, grad_weight, r);
        ...                                             // moment matrix, weighted sums
    }
    weight = __shfl_sync(0xffffffffU, weight, 0, FEATURES);
    for (int d = 0; d < DIM; ++d)
        grad_weight[d] = __shfl_sync(0xffffffffU, grad_weight[d], 0, FEATURES);
    float v = neighbor_volume[j];
    float remote_state = neighbor_state[j * FEATURES + channel];
    blur += remote_state * (weight * v);
    float difference = (remote_state - local_state) * v;
    for (int d = 0; d < DIM; ++d)
        gradient[d] += difference * grad_weight[d];
}
What the profiler showed

Disk seed, C = 16, Nsight Compute at base clocks. Forward: 2.58 ms and 2.02 billion warp instructions, about 33 for each candidate pair. On average only 15.7 of 32 lanes were active, because lanes 1–15 wait while lane 0 computes the weights.

Backward: 2.46 ms, and the load/store unit was 90% busy. Every pair costs three shuffles and some shared-memory loads, on every channel lane.

MethodMeasure first

Every change below started with a measurement and ended with one. These habits made the numbers reliable:

  • Test the cases that training sees. Disk seeds, a uniform texture seed, growing disks, four emoji targets, and four texture targets. We average the targets inside each family, and each family gets the same weight. So the very dense disk does not decide the result alone.
  • Use two timers. Wrapper latency (CUDA events around the Python call) is what training pays. GPU kernel time (from torch.profiler) counts only the kernels. If the two numbers are very different, the time goes to the host: Python and kernel launches.
  • Compare builds in separate processes. Each build has its own CMake folder, and NPA_SPH_EXTENSION_PATH selects which one to load. The order of the builds changes every round, so changes in GPU clock and temperature affect all builds the same way.
  • Read the counters that explain the time. Executed instructions, active threads per warp, occupancy, how busy each unit is, and why warps wait. Instructions divided by candidate pairs is a useful number.
Profiling one kernel (command from BENCHMARKS.md)

  --set basic --export results/sph_profile \

Step 1One lane per particle

The idea comes from the original design. All particles in a grid block are in the same cell. So they all have the same list of candidate neighbors, in the same order.

Now let lane k handle particle k. At loop step j, all 32 lanes read the same neighbor j from shared memory. When all lanes read the same address, shared memory gives the value to all of them in one transaction. This is called a broadcast. No shuffles are needed.

This removes the shuffles and the waiting lanes. Each pair's weights are computed once, by the lane that needs them. If a pair is outside the radius, the lane skips it with continue. The 16 channels of the neighbor's state are read as four float4 values (16 bytes each), also as broadcasts.

New forward, inner loop (one lane per particle)
for (unsigned int j = 0; j < count; ++j) {
    ParticlePosition<DIM> r = config.displacement(position, tile_pos[j]);   // broadcast read
    float d2 = dot(r, r);
    if (d2 >= h2)
        continue;                                   // outside the radius: skip
    float weight, grad_weight[DIM];
    support_weights(config, r, d2, h2, weight, grad_weight);
    float v = tile_volume[j];
    ...                                             // moments, once per pair
    const float4 *remote_state = reinterpret_cast<const float4 *>(&tile_state[j * CHANNELS]);
    #pragma unroll
    for (int q = 0; q < CHANNELS / 4; ++q) {
        float4 packed = remote_state[q];
        float values[4] = {packed.x, packed.y, packed.z, packed.w};
        #pragma unroll
        for (int k = 0; k < 4; ++k) {
            int c = 4 * q + k;
            partial[BLUR + c] += values[k] * (weight * v);
            float difference = (values[k] - local_state[c]) * v;
            #pragma unroll
            for (int d = 0; d < DIM; ++d)
                partial[GRADIENT + c * DIM + d] += difference * grad_weight[d];
        }
    }
}

The first version of this kernel used one warp per grid block. It kept the same formulas and the same order of additions as the first fused kernel. So its forward output was bitwise identical in all 616 tested configurations. The number of executed forward instructions went from 2.02 billion to 234 million, 8.7 times fewer. For 32 channels, two warps share the work (16 channels each), so that each thread does not need too many registers.

Trick

Look for data that many threads need at the same time. Here the grid design already had it: one grid block, one cell, one list of candidates. If all threads read the same address, shared memory gives the value to all of them for the price of one read.

Step 2Not enough warps: warp teams

The new forward took 0.80 ms (at base clocks) instead of 2.58 ms. So it was 3.2 times faster. That is good, but the number of instructions went down 8.7 times, so we expected more. Nsight Compute showed only 14% occupancy and 1.23 instructions per cycle.

The reason: there were too few warps. With one lane per particle, 32,768 particles give only about 1,024 warps. That is about 8 warps per SM. Each warp goes through about 1,900 candidates alone. When a warp waits for memory, the SM has almost no other warp to run.

The fix is to split the loop over neighbors, not the outputs. Each grid block now has four warps, called teams, and all four work on the same 32 particles. The neighbor tiles are dealt like cards: team t takes tiles t, t+4, t+8, and so on. Each team loads its tiles into its own part of shared memory. So the loop only needs __syncwarp (a sync of one warp), not a sync of the whole block. At the end, teams 1–3 add their partial sums into team 0 through shared memory, always in the same order.

Choosing tiles (main loop of each warp)
for (unsigned int remote = first; remote < end; remote += TILE) {
    if (tile_index++ % NEIGHBOR_WARPS != team)
        continue;                         // another team takes this tile
    unsigned int count = min(unsigned(TILE), end - remote);
    __syncwarp();                         // finish reading the previous tile
    if (lane < count) {
        tile_pos[lane] = positions[remote + lane];
        tile_volume[lane] = volume[remote + lane];
    }
    #pragma unroll 4
    for (unsigned int k = lane; k < count * CHANNELS; k += 32)
        tile_state[k] = state[(remote + k / CHANNELS) * FEATURES + first_channel + k % CHANNELS];
    __syncwarp();                         // now the whole warp can read the tile
    if (!valid)
        continue;                         // lanes without a particle only help load
    ...                                   // the pair loop from step 1
}
Adding team sums in a fixed order (simplified reduce_teams)
__syncthreads();                          // this buffer reuses the tile memory
for (int base = 0; base < PARTIALS; base += CHUNK) {
    if (team > 0)                         // teams 1..3 write part of their sums
        for (int e = 0; e < CHUNK; ++e)
            slot[e * 32] = partial[base + e];
    __syncthreads();
    if (team == 0)                        // team 0 adds them: team 1, 2, then 3
        for (int source = 1; source < NEIGHBOR_WARPS; ++source)
            for (int e = 0; e < CHUNK; ++e)
                partial[base + e] += slot_of(source)[e * 32];
    __syncthreads();
}

With more than one team, the float additions happen in a different order. So the results change a little, at roundoff level. Over all test cases, the relative L2 difference was at most 9.1 × 10−7 for outputs and 1.5 × 10−6 for gradients. With NEIGHBOR_WARPS = 1, the code uses the old order again. We used this setting to check the new code bit by bit.

Trick

After you remove work, check that there are still enough warps to hide waiting time. If you already have one lane per output, split the sum (here, the loop over neighbors) across warps. Then add the partial sums at the end in a fixed order.

Step 3Registers, spills, and one build flag

__launch_bounds__(128) tells the compiler that a block has at most 128 threads. With only this, the compiler used 223–250 registers per thread in the forward kernel. Then only 2 blocks fit on one SM, and the gain from step 2 would be lost. The second argument of __launch_bounds__ is the minimum number of blocks that must fit on one SM. This sets a limit on registers:

perception.cuh
// At least 16 resident warps per SM → at most 65,536 / (16 × 32) = 128 registers
constexpr int FORWARD_RESIDENT_WARPS = 16;
template <int DIM, int FEATURES, BoundaryCondition BC>
__global__ void __launch_bounds__(ForwardLayout<DIM, FEATURES>::THREADS,
                                  ForwardLayout<DIM, FEATURES>::MIN_BLOCKS) forward(...)

With this limit, the kernels spilled registers to slow memory. To study this, we compiled only the perception kernels in a small test file with -Xptxas -v. This takes a few seconds instead of the 80 seconds of the full build, and it prints the spills of each kernel. The result was strange: the small test file almost did not spill, but the real build spilled a lot. The difference was one CMake setting:

ptxas -v output: forward kernel, C = 16, 96 registers
# standalone translation unit
8 bytes stack frame, 4 bytes spill stores, 8 bytes spill loads
# same kernel with -rdc=true (relocatable device code)
152 bytes stack frame, 468 bytes spill stores, 720 bytes spill loads
CMakeLists.txt
# One translation unit without device-side launches: whole-program device
# compilation lets ptxas allocate registers without relocatable-code limits
# (relocatable builds spill in the fused perception kernels).
set_property(TARGET sph_cuda PROPERTY CUDA_SEPARABLE_COMPILATION OFF)

Separable compilation (-rdc) is only needed when GPU code calls functions in another .cu file. This extension has only one .cu file. Turning it off removed the spills.

Then we raised the forward kernel's limit to 128 registers (at least 16 warps per SM instead of 32). This removed the last small spill. The final forward kernel uses 123–126 registers and no stack. This is the last row of the table in step 2.

Two smaller changes also helped. The loop that adds the team sums stays rolled (#pragma unroll 1), so the compiler does not load the values of all teams at once. And the loop that loads tiles is unrolled only 4 times.

Trick

cuobjdump --dump-resource-usage shows registers, stack, and shared memory for every kernel in a built library. -Xptxas -v on a small test file gives fast answers. But always use the same build flags as the real build.

Step 4The density kernel and the grid build

After the feature kernels became fast, the density pass was 23% of the forward kernel time. It still used one warp per particle, with a shuffle sum for each particle. We rewrote it in the same style: one lane per particle, and neighbor positions and masses in team tiles. On the disk seed, it went from 134 to 99 µs. The average forward speedup went from 4.17× to 4.48×.

The grid build had an easier win. In the count pass, atomicAdd returns the old count of the cell. This old count is the rank of the particle inside its cell. If we save it, the scatter pass does not need its own atomicAdd, and it does not need the extra array for it.

Count pass: save the rank
uint32_t prev_count = atomicAdd(&cell_counts[cell_idx], 1U);
rank_in_cell[idx] = prev_count;           // stored in the permutation buffer
Scatter pass: no second atomic
// before: write_idx = atomicAdd(&bin_write_indices[cell], 1U);
permutation[idx] += bin_offsets[batch_idx * config.cell_count + hash]
                    - batch_idx * config.particle_count;

We also removed memsets for buffers that are always fully overwritten (permutation, bin offsets, block offsets). The two counter arrays now share one allocation, so one memset clears both. A grid build now uses 9 launches instead of 14. All of them run on the caller's CUDA stream.

Step 5Fast kernels, slow host

After steps 1–4, the GPU was busy for only about 54 ms of a 135 ms emoji training epoch (measured in the profiler). Each rollout step launched about 89 small kernels, and Python could not launch them fast enough.

To measure only the host cost, we ran the step on a very small problem, where GPU time is almost zero:

Host time per call (tiny problem)BeforeAfter
Grid build + binning + perception, forward216 µs119 µs
NPA training step, forward572 µs447 µs
NPA training step, forward + backward1,190 µs990 µs

Before: grid.instantiate (47 µs), bin_particles (59 µs), and perception (110 µs) were separate calls. After: one call of 119 µs. Of this, 45 µs is the C++ call, 8 µs is memory allocation, and the rest is autograd and Python. Each tensor passed through nanobind costs about 2 µs, and each kernel launch costs 2–3.5 µs.

The fix is one autograd function, with one C++ call for the forward and one for the backward:

  • The forward call builds the grid, sorts positions and states into cells, and runs the density and feature kernels.
  • The backward call computes the perception gradient, adds the gradient that reaches s_bin from the rest of the model, and moves the result back to the original order.
  • The grid data lives in one int32 buffer, and the saved values live in one float buffer. So 28 tensor conversions became 9.
  • When there are no masses, the code reads a buffer of ones that it keeps between steps. Before, it made and sorted a new one in every step.
sph.py (simplified)
class FusedPerception(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, s, mass, grid, eps0, density_grad, log_norm_grad,
                log_norm_density_grad, save_backward):
        snapshot = x.new_empty(hashgrid.fused_snapshot_words, dtype=torch.int32)
        x_bin, s_bin = torch.empty_like(x), torch.empty_like(s)
        output = s.new_empty(B, N, C * (2 + dim) + (dim if density_grad else 0))
        workspace = s.new_empty(hashgrid.fused_workspace_size(...))
        hashgrid.fused_perception_forward(x, s, mass, eps0, snapshot, x_bin, s_bin,
                                          output, workspace, ..., stream)   # one call
        ctx.save_for_backward(x_bin, workspace, eps0, snapshot)
        return output, x_bin, s_bin, snapshot

    @staticmethod
    def backward(ctx, grad_output, grad_x_bin, grad_s_bin, _):

Trick

Autograd would add the two gradients of s_bin (one from perception, one from the Euler update) with one a + b. The unbinning kernel does the same single addition. a + b and b + a give the same float, so the result is bit-for-bit the same.

The emoji epoch went from 87 to 77 ms. Most of the remaining host time is in the MLP and the Euler update, which are plain PyTorch. The optional NPA(compile_step=True) compiles them and saves another 7–11%.

Step 6Hidden syncs in the loss

The loss draws the particles into images. This is called splatting. The old code used a Python loop over the batch. For each sample, it kept only the kernel taps inside the image, with a boolean mask.

To index with a boolean mask, PyTorch must know how many values are true. So the CPU must wait for the GPU: a host sync. This happened 8 times per forward pass, and more times in the backward. At each sync, the GPU runs out of work and waits until Python catches up.

utils/splatting.py: one pass for the whole batch
# before, per sample: flat_idx = (y_idx * img_size + x_idx)[mask]   ← host sync
flat_idx = (y_idx.clamp(0, img_size - 1)[..., :, None] * img_size
            + x_idx.clamp(0, img_size - 1)[..., None, :]
            + (torch.arange(B, device=device) * img_size * img_size)[:, None, None, None])
w = torch.where(mask, g, 0.0)        # taps outside the image add exactly 0
c = torch.where(mask[..., None], colors[:, :, None, :] * w[..., None], 0.0)
density.scatter_add_(0, flat_idx.reshape(-1, 1), w.reshape(-1, 1))
rgb.scatter_add_(0, flat_idx.reshape(-1, 1).expand(-1, 3), c.reshape(-1, 3))

The new code does not remove the taps outside the image. It clamps their index to a valid pixel and adds exactly zero there. So all tensors have a fixed shape, and nothing needs to count the taps. The second where makes sure that a NaN or Inf color of a particle outside the image does not reach the image or the gradients. On CPU, the new images are bitwise equal to the old ones.

This small change had a big effect. With the fast kernels and the old splatting, the emoji backward still took 72 ms per epoch. With the new splatting, it took 40 ms, because the GPU no longer stops between samples.

MethodChecking that results stay correct

A faster version is only useful if the results stay the same. We checked in layers, from the strictest test to the loosest:

  1. Bitwise A/B on the same input. Binning uses atomics, so the order of particles inside a cell changes from run to run. Then every sum changes a little. So the A/B script saves one grid snapshot (sorted positions, offsets, block info) and gives the same snapshot to both builds. With this, the old fused kernels give the same bits every time. The new kernels with NEIGHBOR_WARPS = 1 gave the same bits as the old ones in 2D.
  2. Tolerance tests against other code. A simple dense PyTorch version (sphops/testing/torch_sph.py) and the original SPH operators. The tests cover 2D and 3D, both boundaries, normal and padded channel counts up to 32, block sizes 16/32/64, different masses, singular moment matrices, and the periodic seam.
  3. Gradient checks at the saved point. log(1 + |g|) first rounds 1 + |g|. For a tiny g, a change in the last bits can change the derivative. So the test computes the reference gradient at the values that the fused kernel saved. Then both sides use exactly the same point.
  4. Compute Sanitizer. memcheck, synccheck, initcheck (it finds a removed memset that was still needed), and racecheck (for the per-warp tiles and the reused shared buffers).
  5. Matched training runs. Same weights, same pool, same sampling, and the same number of steps. Repeated timings were within 0.3%. We compared loss differences with the normal run-to-run noise of the old code.
Problems we hit

A ReLU input very close to zero (below 10−5) can have a different sign in two correct versions. Then the gradient of a whole neuron changes. So the parameter-gradient test needs a special case for this.

With kernel filters, initcheck reports false errors: memory written by kernels outside the filter looks uninitialized. Racecheck on all kernels needed more than 11 GB of CPU memory. Limiting it to the changed kernels needed only a few GB.

TakeawaysChecklist for your next kernel

  1. Look for structure that the data already has. Particles in one grid block share one list of candidates. This one fact made broadcast reads possible.
  2. Count instructions per unit of useful work. Also check how many lanes are active. If one lane works while 15 wait, the profiler shows it, but it is easy to miss.
  3. Shuffles and shared-memory loads use the same hardware unit. A loop with three shuffles per pair can be limited by this unit, even with little math.
  4. After you remove work, check the parallelism again. Low occupancy with few warps per SM means nothing hides the waiting time. Split the sum across warps.
  5. Check registers and spills with the real build flags. Use __launch_bounds__ with a minimum block count, -Xptxas -v, and cuobjdump.
  6. Reuse what an earlier pass already knows. The return value of atomicAdd is a free rank.
  7. When the kernels are fast, profile the host. Count kernel launches and tensor conversions per step. Look for hidden syncs, like boolean-mask indexing or .item().
  8. Test in layers. Bitwise where the order allows it, tolerances against a reference everywhere, sanitizers for memory and races, and matched training compared with the noise of the old code.
