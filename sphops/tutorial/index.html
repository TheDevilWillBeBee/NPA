Fused perception: how the work is distributed on the GPU

This guide explains the CUDA code that computes perception in Neural Particle Automata (NPA). It starts from the original hash-grid design and shows, with pictures, which thread does which work, in which order, and where the data sits at each moment. One idea is the backbone of every kernel: a grid block of particles reads its neighbor candidates into shared memory, tile by tile, and then runs a nested loop over (my particle, candidate). Every change below only changes how threads are mapped onto this loop.

Setup for all numbers, unless a section says otherwise: RTX 4090, 2D, a batch of 8 × 4,096 particles, 16 state channels (C = 16), at most 32 particles per grid block. Numbers come from sphops/BENCHMARKS.md, sphops/FUSED_PERCEPTION.md, or the six Nsight Compute reports in sphops/ncu_reports/fused_vs_unfused_20261008/. Each number says where it comes from. "Original" means the standalone SPH operators in sph_cuda.cu. "First fused version" means the fused kernels of commit 0ebb5d0, which this work replaced.

Before we startWords used here

Kernel
A function that runs on the GPU. In SPH, "kernel" also means the weight function W. This guide says "SPH kernel" for that.
Thread, warp, lane
A warp is a group of 32 threads that run the same instruction together. A lane is one thread of a warp.
CUDA block, SM
A CUDA block is a group of warps that runs on one SM (one of the GPU's processors). The RTX 4090 has 128 SMs. An SM can hold at most 48 warps at the same time.
Grid, cell
The hash grid divides space into square cells. The cell size is the perception radius ε.
Grid block
Up to max_particles_per_block particles (32 in the 2D configs) of one cell. A crowded cell is cut into several grid blocks. One CUDA block processes one grid block.
Binned order
The order of particles after sorting them by cell. All particles of a cell are next to each other in memory.
Candidate, neighbor
A candidate is a particle in one of the 9 cells (27 in 3D) around our cell. A neighbor is a candidate whose distance is below ε. Only neighbors contribute.
Tile
Up to 32 consecutive candidates, copied together into shared memory.
Team
One warp of a CUDA block in the fused kernels. A CUDA block has 4 teams. They all work on the same 32 particles but on different tiles.
Shared memory
Small, fast memory on the SM that all threads of one CUDA block can read and write.
Register, spill
Registers are the fastest memory. Each thread has its own. An SM has 65,536 of them. If a thread needs more than the compiler can give, extra values go to slow local memory. This is called a spill.
Broadcast
When all 32 lanes read the same shared-memory address in one instruction, the hardware serves them with one transaction.
Sector
Global memory moves in 32-byte sectors. A store that uses 4 bytes of a sector still costs the whole sector.
Occupancy
How many warps are resident on an SM, compared with 48. While one warp waits for memory, the SM runs another. More warps hide more waiting.
Host, launch, sync
The host is the CPU side (Python and C++). A launch is the host telling the GPU to run a kernel. A sync is the host waiting until the GPU finishes.

BackgroundWhat perception computes

Each particle i has a position xi, a fixed mass mi, and a state si with C channels. Perception looks at all neighbors closer than ε. It uses two SPH kernels: the smooth poly6 kernel W and the gradient of the spiky kernel, ∇W.

  • Density: ρi = Σj mj W(rij). Each particle then has a volume Vj = mj / ρj.
  • Blur: s̄i = Σj Vj sj W(rij).
  • State gradient: ∇si = Σj Vj (sj − si) ∇W(rij), corrected with the inverse of the moment matrix Mi = Σj Vj ∇W(rij) ⊗ rij. The correction only changes the forward value. The backward pass ignores it (a straight-through estimator).
  • Density gradient: ∇ρi = Σj mj ∇W(rij), divided by the total mass of the sample.
  • Scaling and log normalization of both gradients: log(1 + |g|) · g / |g|.

The output row of a particle is [s, s̄, ∇s, ∇ρ]. It has C(2 + D) + D numbers: 66 for C = 16 in 2D. The NPA's MLP reads it. Every term is a sum over neighbors. So the cost of perception is the cost of visiting pairs (i, j).

The core ideaThe backbone: a grid block, its candidates in tiles, and a nested loop

All kernels in this guide, old and new, have the same skeleton. A CUDA block takes one grid block. All particles of a grid block lie in the same cell, so they all have the same candidates: the particles of the 9 cells around that cell (27 in 3D). The CUDA block walks through these candidates in tiles. For each tile, all threads together copy the tile from global memory into shared memory. Then each thread runs the inner loop over the tile for its own particle. Only the mapping of threads to particles and channels changes between the versions.

In the current code this loop is one helper, for_each_neighbor, used by the density, forward and backward kernels. A TileCursor walks the tiles that belong to this team (tile k goes to team k mod 4, see step 5). The load callback issues asynchronous copies of one tile into one of the warp's two shared buffers, and the pair callback does the work for one (my particle, candidate) pair that passed the distance test. With two buffers, the copies of the next tile are in flight while the current tile is processed (step 10):

The rest of this guide follows the order of the work: how particles become grid blocks and CUDA blocks (step 1), how a block finds its candidates (step 2), how the original kernels mapped threads onto the loop (step 3), and how the fused kernels map them (steps 4 to 8). Step 9 looks at the host.

Step 1From particles to CUDA blocks

The grid build is a counting sort. It runs in three passes on the GPU: count, scan, scatter. Then a fourth pass writes one BlockInfo record for each grid block. We follow a small example: a 4 × 4 grid, 12 particles (a to l), and max_particles_per_block = 4. Cells are numbered with x changing fastest: cell 4y + x.

Measured: the empty tail

In 2D (16 × 16 cells, N = 4,096, cap 32) the launch is min(4,096, 256 + 128) = 384 blocks per sample, 3,072 for the batch of 8 (grid size in all six Nsight reports). The shape case uses 218 of the 384 per sample (geometry above), so about 43% of the launched CUDA blocks exit at once. In 3D (32³ cells, N = 16,384, cap 64, batch 4) the launch is min(16,384, 32,768 + 256) = 16,384 per sample, 65,536 in total (Nsight report ball_3d). The ball seed has about 3.7 particles per occupied cell (BENCHMARKS.md), so about 4,400 blocks per sample have work and about 73% of the records are empty. Since the second round (step 10) the kernels no longer launch one CUDA block per record: a CUDA block loops over the records blockIdx.x, blockIdx.x + gridDim.x, … and stops at the first empty one, and the launch is at most eight waves of resident blocks (4,096 for the forward in 3D instead of 65,536). The empty tail then costs one record read (32 bytes since step 11) per CUDA block.

The whole grid build is 6 launches: one memset for both counter arrays, the count kernel, two kernels for one CUB scan that produces bin_offsets and block_offsets at once (a scan over zipped pairs), the scatter kernel, which in the fused path also copies positions, states and masses into binned order, and the record kernel, which also writes the empty tail. All of them are ordered on the caller's CUDA stream. It used to be 14 launches (BENCHMARKS.md), then 9 after the rank trick and the removal of memsets for buffers that are fully overwritten anyway, and 6 since the second round (step 10).

Step 2Neighbor ranges: three spans, or nine

Cells are numbered with x changing fastest. So the three cells of one row of the 3 × 3 neighborhood are consecutive cell numbers, and in binned order their particles form one contiguous span. A grid block does not need nine lookups. It reads three spans: one per row, from bin_offsets[first] to bin_offsets[last + 1].

With periodic boundaries, a row can cross the edge of the domain. The left neighbor of cell x = 0 is cell x = grid_size − 1, which sits at the other end of the row in memory. So the code visits a second, disjoint chunk for that row. This is the wrap loop in the backbone, with WRAP_CHUNKS = 2 for periodic grids and 1 otherwise. The helper row_x_range gives the x range of each chunk: the up to three adjacent cells for chunk 0, and the single wrapped cell for chunk 1.

__device__ __forceinline__ bool neighbor_span(const int *cell, unsigned int batch, int row, int wrap_chunk,
                                              const uint32_t *bin_offsets, uint32_t &start, uint32_t &end) const
{
    int neighbor[DIM], first_x, last_x;
    if (!neighbor_row(cell, row, neighbor) || !row_x_range(cell, wrap_chunk, first_x, last_x))
        return false;
    neighbor[0] = first_x;
    unsigned int first = cell2hash(neighbor);
    neighbor[0] = last_x;
    unsigned int last = cell2hash(neighbor);
    start = bin_offsets[batch * cell_count + first];
    end = bin_offsets[batch * cell_count + last + 1];
    return start != end;
}

In 3D the neighborhood is 3 × 3 × 3 cells. Only x is contiguous, so there are 3 × 3 = 9 rows, each a span of three x-adjacent cells. NEIGHBOR_ROWS is 9 and the row index encodes (y, z) offsets as row / 3 and row % 3.

Step 3The original mapping: one thread per (particle, channel)

In the original code, every SPH operator is one instance of a template kernel forward_kernel<DIM, COMP_TYPE, STRIDE>: count, density, density gradient, moment matrix, blur, gradient. Each one has a backward twin. All of them run the backbone loop. The blur and gradient kernels use 256 threads per CUDA block and tiles of 64 candidates. They map one thread to one (particle, channel) pair:

sph_cuda.cu · forward_kernel, blur part (one thread per particle and channel)
if constexpr (COMP_TYPE == ComputationType::Blur)
{
    for (uint32_t i = threadIdx.x; i < local_chunk * output_dim; i += blockDim.x)
    {
        uint32_t particle_idx = features.row(i);
        uint32_t feature_idx = features.col(i);
        ParticlePosition<DIM> p_i = local_pos[particle_idx];
        float output = 0.0f;
        for (uint32_t j = 0; j < remote_chunk; ++j)
        {
            ParticlePosition<DIM> p_j = neighbor_pos[j];
            if (config.l2_distance(p_i, p_j) < eps2)
            {
                float v_j = neighbor_density_rcp[j];
                float s_j = neighbor_state[j * feature_dim + feature_idx];
                ParticlePosition<DIM> r_ij = config.displacement(p_i, p_j);
                float w_ij = smoothing_kernel(r_ij, config.eps);
                output += s_j * w_ij * v_j;
            }
        }
        local_buffer[i] += output * config.smoothing_coef;
    }
}

With 16 channels, a warp holds 2 particles × 16 channels. All 32 lanes run the inner loop with the same j. The read of neighbor_pos[j] is already a broadcast: one address for all lanes. The read of neighbor_state[j * feature_dim + feature_idx] touches 16 consecutive floats, which shared memory also serves in one go. So the memory side was good from the start. The cost is in the arithmetic: the distance test, the SPH weight and the displacement are the same for all 16 channel threads of a particle, and every one of them computes them.

The second cost is the number of passes. models/npa.py built perception in PyTorch from these operators. The forward pass visits all candidates five times (density, blur, moment matrix, gradient, density gradient), with the matrix inverse, the moment correction, the scaling, the log normalization and the concatenation as separate PyTorch kernels in between. Positions are detached during training, so the backward pass visits the candidates twice (blur and gradient, state adjoint only) and runs the PyTorch adjoints of the glue.

Step 4The fused forward mapping: one lane per particle

The fused path uses four kernels instead of five operators plus glue. density_forward computes the density, the volumes and the density gradient. forward computes the blur, the raw gradient, the moment matrix, the correction, the normalization and writes the packed output row. backward_prepare and backward are step 7. NPA trains with fixed masses and detached positions, so only the state adjoint is needed. This is what makes the fusion simple.

The mapping is the change: lane k owns particle k of the grid block, with all of its channels. Before the loop, the lane loads its own position and its 16 state values into registers (four float4 loads). For every candidate, the lane computes the distance, W and ∇W once, and then updates all 16 blur sums, 32 gradient sums, the 3 moment terms and the 2 weighted sums. If the candidate is outside the radius, the lane skips it with one continue, for all channels at once.

Step 5Not enough warps: warp teams

After step 4, the first version of the new forward kernel used one warp per grid block: a CUDA block of 32 threads. The instruction count had dropped a lot, but the time dropped less. The reason is parallelism. A grid block gives the GPU only one warp, and that warp walks through hundreds or thousands of candidates alone. The whole call has only about 1,100 to 1,750 grid blocks (section on arrangements), so the 128 SMs get about 9 to 14 warps each, and the dense blocks run much longer than the others. When a warp waits for shared memory or for the next tile, the SM has almost nothing else to run.

Measured: one warp per grid block

Nsight Compute report of this intermediate version, dense disk, C = 16, forward kernel: 32 threads per CUDA block, 95 registers per thread, achieved occupancy 13.8% (6.6 active warps per SM out of 48), 1.23 instructions per cycle, no eligible warp in 66% of the cycles. This report is local (results/kernel_opt_20261007/ncu/v1_growing_seed_c16_forward.ncu-rep) and not source-controlled; it is not one of the six reports in sphops/ncu_reports/.

The fix splits the loop over tiles, not the outputs. A CUDA block now has 4 warps, called teams. All four hold the same 32 particles in their lanes. The tiles are dealt round-robin: team t takes tiles t, t + 4, t + 8, …. Each team loads its tiles into its own part of shared memory. So inside the loop a team only needs __syncwarp, never a barrier of the whole block. At the end, the four partial sums of each lane must be added. Teams 1 to 3 write their partials into shared memory, and team 0 adds them in the fixed order 1, 2, 3. Then team 0 owns the output.

template <int PARTIALS, typename Layout>
__device__ __forceinline__ void reduce_teams(
    float *partial, float *buffer, unsigned int team, unsigned int group, unsigned int lane)
{
    if constexpr (NEIGHBOR_WARPS > 1) {
        __syncthreads();  // Staging aliases tiles that other warps may still read.
        #pragma unroll
        for (int base = 0; base < PARTIALS; base += Layout::CHUNK) {
            if (team > 0) {
                float *slot = buffer + ((team - 1) * Layout::SPLIT + group) * Layout::CHUNK * 32 + lane;
                #pragma unroll
                for (int e = 0; e < Layout::CHUNK; ++e)
                    if (base + e < PARTIALS)
                        slot[e * 32] = partial[base + e];
            }
            __syncthreads();
            if (team == 0) {
                // Rolled: hoisting every team's loads would spill the partials.

Step 6Output staging: full sectors instead of 4 bytes

Nsight Compute flagged the stores of the fused forward kernel as uncoalesced. The reason is the lane-per-particle mapping. Each lane owns one output row of 66 floats (264 bytes). When the 32 lanes of team 0 store element c of their rows in one instruction, the 32 addresses are 264 bytes apart. Each address falls into a different 32-byte sector, and only 4 bytes of each sector are written. The memory system still moves the whole sector.

Step 7Backward: prepare once, then gather

The fused backward has two kernels. backward_prepare runs one thread per (particle, channel). It reads the incoming gradient row of the particle, undoes the log normalization and the radius scaling for its channel, writes the self term of the state adjoint, and writes the per-neighbor cotangents in a layout that the gather kernel can load as tiles: [particle][component][channel], with component 0 the blur cotangent and components 1 and 2 the two gradient cotangents. Then backward runs the backbone again: a lane per particle, four teams, tiles of cotangents, and no atomics.

Why a gather works: W is symmetric and ∇W changes sign when i and j are swapped. So the contribution of pair (i, j) to the adjoint of sj can be computed from the side of j as a sum over its own neighbors, with the volume Vj applied once at the end. The original backward kernels used the same gather for the state adjoint. Their general versions also computed position and density adjoints, where several channel threads of one particle add to the same value, and they used atomicAdd into shared-memory buffers for that. The fused backward has no position or density adjoints, so it has no atomics.

Step 8Registers and occupancy

One lane of the forward kernel keeps 71 named floats: its position (2), its state (16), the blur sums (16), the raw gradient sums (32), the upper half of the moment matrix (3) and the weighted gradient sum for the backward pass (2). On top of that come the displacement, the distance, the two weights, the loop state and the addresses. The compiler needs to fit all of this into registers, or it spills.

The __launch_bounds__ attribute controls this. Its first argument is the block size (128 threads). Its second argument is the minimum number of CUDA blocks that must fit on one SM. An SM has 65,536 registers, so MIN_BLOCKS = 4 means at most 65,536 / (4 × 128) = 128 registers per thread. The constants in the header express this as resident warps: FORWARD_RESIDENT_WARPS = 16 gives MIN_BLOCKS = 16 / 4 = 4.

Step 9The host side: launches, autograd and hidden syncs

After steps 4 to 8 the kernels were fast, but a training step is more than kernels. The host must launch every kernel, and Python and autograd add their own time. Each launch costs a few microseconds of CPU time, and when the GPU finishes its work before the host has launched the next kernel, the GPU waits. The step was host-bound. Two changes reduced the host work.

One call per direction. In the original path, models/npa.py called the grid build, the binning and six autograd Functions one by one, and PyTorch ran the glue in between. Now one autograd Function, FusedPerception, makes one C++ call for the forward and one for the backward. The forward call builds the grid, bins positions and states, and runs the density and feature kernels. The backward call runs the two backward kernels and moves the result back to the original particle order. The grid data lives in one int32 buffer and the saved values in one float buffer, so fewer tensors cross the Python to C++ boundary. When there are no masses, the kernels read a persistent buffer of ones instead of binning a new one every step.

No hidden syncs in the loss. The loss draws particles into images. The old code did this sample by sample and kept only the kernel taps inside the image with a boolean mask. To index with a boolean mask, PyTorch has to know how many entries are true, so the CPU waits for the GPU: a host sync, 8 times per loss forward and more in the backward. The new code clamps the index of an off-image tap to a valid pixel and adds exactly zero there. All shapes are fixed, nothing needs counting, and the batch is drawn in one pass.

Step 10A second round: loads in flight, fewer launches

After this guide was written, we went through the kernels once more with Nsight Compute. The stall reasons told the story. In the sparse cases the forward kernel waited for global loads and at barriers; in the periodic cases every pair paid for a fmodf in the displacement; the backward waited for shared-memory loads; and in 3D most of the 65,536 launched CUDA blocks only read an empty record. The changes below keep the backbone and the lane-per-particle mapping. All of them together are in sphops/BENCHMARKS.md under "Second optimization round".

  • Tiles in flight. Each warp now has two tile buffers. The load callback issues cp.async copies (global to shared, no registers) for the next tile and commits them as one group, then the warp processes the current tile. A cp.async.wait_group and a __syncwarp make the next tile visible. The backward tile shrank to 8 candidates so that two buffers still fit the shared-memory budget. This removed most of the global-load stalls.
  • Persistent grid blocks. A CUDA block loops over the records blockIdx.x, blockIdx.x + gridDim.x, … and stops at the first empty one. The launch is at most eight waves of resident blocks, so the 2D launch is unchanged and the 3D launch drops from 65,536 to 4,096 blocks.
  • Fewer instructions per pair. The volume-weighted weights VjW and Vj∇W are computed once per pair, so each channel costs one fused multiply-add for the blur and one per dimension for the gradient (4 instead of 5 floating-point instructions per channel in 2D). The exact (sj − si) form is kept. A version that centered the tile states on a per-block reference state saved one more instruction per channel, but it was measurably less accurate against a float64 reference, so it was not kept.
  • Fewer barriers. The team reduction exchanges all partial sums in one chunk (the staging may grow to 21 KB, which still leaves four resident blocks), and both output row sets are staged behind each other and copied after one barrier: 4 block barriers per grid block instead of 10.
  • Periodic displacement without fmodf. The wrap is now d − L · rint(d / L), one rounding and one fused multiply-add. A displacement already inside the box is returned exactly.
  • Host side. The scatter pass also copies positions, states and masses into binned order, the record kernel writes the empty tail itself, the two prefix sums run as one scan over zipped pairs, and the unbinning kernel moves rows as float4. A fused forward is 8 launches instead of 12.

Step 11Several lanes per particle

Step 10 ended with the profile's verdict: in the sparse arrangements half of the lanes are idle. The reason is the mapping of step 4. A grid block with six particles runs a warp with six working lanes, and every one of them walks all candidates of every tile. The ball seed in 3D has about ten particles per cell, the shapes have thin boundaries, and even the dense disk ends every block with a ragged last pass. The fix keeps the backbone and changes only who walks the candidates: when a pass has at most 16, 8 or 4 particles left, each particle gets 2, 4 or 8 lanes.

The pass loop of each kernel chooses the share per pass, uniformly for the block, so no branch diverges inside a warp. slot is the particle within the pass, sub the lane's rank within its particle. The share is also capped by the block's candidate density (share_cap): the butterfly costs one shuffle per partial sum and step, 53 partials in the 2D forward and 73 in 3D, so eight lanes per particle only pay when each tile has enough candidates to split. The density is a new field of the block record, candidates_per_row, which the record kernel of step 1 sums from the span bounds once per cell (the record grew from 16 to 32 bytes):

The gains shrink as the cells fill up: at N = 32,768 on a 16 × 16 grid almost every block holds 32 particles and shares nothing. In 3D the ball keeps its radius, so N sets the particles per cell: about 1 at 4,096, 13 at 16,384 (the configured case), 50 at 65,536. The two smallest 3D counts are where the cap matters: with lanes shared by the particle count alone the 3D forward was 21% and 13% slower there (a tile holds about three candidates, and the butterfly has nothing to split); with the cap it is 5% and 2% slower, the fixed cost of the sharing machinery in blocks with almost no work.

The durations fall less than the instruction counts because the sparse kernels wait more than they issue: the per-pass work (tile copies, barriers, the team reduction, the epilogue) is the same whether a particle has one lane or eight, and the periodic uniform forward is dominated by it. Four variants were measured and dropped. Summing the span lengths inside the neighbor kernels instead of in the record kernel (every warp walks the nine spans of its block before the pass loop) cost as much in 3D as the regression it removed; using the cell's own particle count as the density (free) fixed 3D but capped the boundary blocks of the dense disk, whose cells are nearly empty while their neighbor rows are full, and lost half of the dense gain. Contiguous candidate ranges per lane (lane r takes candidates r · chunk to (r + 1) · chunk − 1) keep the stride-1 loop but make the lanes of one particle read tile rows that are a multiple of 32 banks apart: three times the bank conflicts and a slower backward. Padding the staged rows to an odd number of float4 removes even the conflicts of the interleaved version (3D backward: 7.6 million to 31 thousand), but no kernel got faster and the larger tiles cost occupancy; the conflicts were not on the critical path.

MethodChecking correctness

A faster kernel is only useful if it gives the same answer. The checks, in order of strictness (BENCHMARKS.md):

  1. Bitwise A/B on the same snapshot. Binning uses atomics, so the particle order inside a cell changes between runs, and then every sum changes a little. The A/B script saves one grid snapshot and gives it to both builds. With NEIGHBOR_WARPS = 1 the forward was bitwise identical to the first fused version in all 616 configurations; the backward was identical in 2D and within 8.7 × 10−8 relative L2 in 3D.
  2. The shipped configuration (4 teams) differs from the first fused version by at most 9.1 × 10−7 relative L2 in outputs and 1.5 × 10−6 in state adjoints. Against the original operators: at most 6.5 × 10−7 and 1.8 × 10−6.
  3. Gradient checks at the saved point. log(1 + |g|) rounds 1 + |g| first, so for a tiny g the derivative can change with the last bits. The tests compute the reference adjoint at the exact values the fused kernel saved.
  4. Compute Sanitizer. memcheck, synccheck, initcheck and racecheck report no errors. Racecheck on all kernels needed more than 11 GB of host memory, so it runs with kernel-name filters.
  5. Matched training runs with the same weights, pool, sampling and step counts. Timings repeat within 0.3%. Loss differences are at the level of the run-to-run noise of the old code (about 1% median per epoch, because binning and scatter_add use atomics).
